# Design: Multi-Agent Orchestration & Trajectory Evaluation Framework

## Executive Summary
This document specifies the architecture, public interfaces, message protocols, context isolation boundaries, failure mode mitigations, and benchmark evaluation metrics for a three-agent system (**Planner**, **Executor**, **Critic**).

The system targets the Task 3 repository codebase (`Task-3_Agent_Loop_Mcp`) to evaluate agent disagreement dynamics, anti-sycophancy prompts, context isolation, revision loop controls with escalation, and benchmark performance across four comparative baseline configurations. Latest benchmark: **100% critic catch rate** across all critic configs with **0% rubber-stamp rate**; Config D achieves lowest cost at 2,852 tokens/task (28.2s).

---

## 1. Public Interfaces & Typed Message Protocols

All inter-agent communication uses strongly-typed TypeScript interfaces and Zod validation schemas (`packages/orchestrator/src/types/messages.ts`):

```typescript
// Plan: Generated by Planner for Executor
export interface Plan {
  taskId: string;
  originalTask: string;
  approach: string;
  affectedFiles: string[];
  expectedOutcome: string;
  risks?: string[];
  clarifyingQuestion?: string; // Set when task is ambiguous
}

// Patch: Code changes produced by Executor for Critic
export interface Patch {
  taskId: string;
  planId: string;
  filePath: string;
  code: string;           // Code patch content
  reasoning: string;      // Executor self-reasoning (STRIPPED from Critic)
  testsPassed?: boolean;
  issues?: string[];
}

// Issue raised by Critic
export interface CriticIssue {
  severity: 'blocker' | 'minor';
  note: string;
  location?: string;
}

// Review: Verdict emitted by Critic
export interface Review {
  patchId: string;
  verdict: 'approve' | 'revise';
  issues: CriticIssue[];
  turnsUsed: number;
  confidence?: number;
}

// RevisionRequest: Sent to Executor upon revision verdict
export interface RevisionRequest {
  taskId: string;
  patchId: string;
  review: Review;
  maxRevisionRounds: number;
  roundsRemaining: number;
}

// EscalationResult: Triggered when revision cap is reached without approval
export interface EscalationResult {
  taskId: string;
  reason: 'max-revisions-hit';
  lastReview: Review;
  lastPatch: Patch;
  criticHistory: Review[];
  recommendation: string;
}

// Trajectory: Complete execution log of a run
export interface Trajectory {
  taskId: string;
  category: 'well-specified' | 'seeded-flaw' | 'ambiguous';
  task: string;
  plan?: Plan;
  patches: Patch[];
  reviews: Review[];
  escalation?: EscalationResult;
  finalOutcome: 'approved' | 'escalated' | 'clarification-requested';
  totalTurns: number;
  totalTokens: number;
  wallClockMs: number;
}
```

## 2. Context Isolation Boundaries

The `ContextAssembler` strictly builds agent context to isolate information boundaries:

* **Planner Context**: Task prompt + codebase snapshot (`Task-3_Agent_Loop_Mcp`).
* **Executor Context**: Task prompt + Plan + codebase snapshot.
* **Critic Context**: Original task prompt + raw code patch string ONLY (**Executor reasoning and prior turn history are completely redacted**).

---

## 3. Three Primary Failure Modes & Mitigations

1. **Sycophantic Critic**:
   - *Risk*: Critic approves faulty patches because it is persuaded by the Executor's self-reasoning.
   - *Mitigation*: Strict context isolation (stripping `patch.reasoning`) and adversarial anti-sycophancy prompt framing. Tested via seeded-flaw benchmark tasks.

2. **Confabulated Blockers**:
   - *Risk*: Critic invents false issues to seem thorough.
   - *Mitigation*: Distinction between `blocker` (must fix) vs `minor` (suggestions) severity levels. Only `blocker` issues trigger a `revise` verdict.

3. **Context Leakage**:
   - *Risk*: Author reasoning bleeds into review prompts.
   - *Mitigation*: Dedicated `ContextAssembler` and unit test assertions verifying context isolation.

## 4. Benchmark Baseline Configurations

The evaluation compares 4 configurations across 15 golden tasks:
- **Config A**: Single-Agent Baseline (Executor only).
- **Config B**: Executor + Critic with uncapped revision loop (max 10 rounds).
- **Config C**: Executor + Critic with revision cap = 3 rounds.
- **Config D**: Full Strict Context Isolation (Config C + verified isolation).

### Latest Benchmark Results (15 tasks × 4 configs)

| Metric | Config A | Config B | Config C | Config D |
|--------|----------|----------|----------|----------|
| Task Success Rate | 1.000 | 0.867 | 0.467 | 0.667 |
| Critic Catch Rate | N/A | 1.0 | 1.0 | 1.0 |
| Rubber-Stamp Rate | N/A | 0.0 | 0.0 | 0.0 |
| Mean Revision Rounds | 1.00 | 3.60 | 2.27 | 1.73 |
| Tokens / Task | 1,556 | 5,879 | 3,855 | 2,852 |
| Wall-Clock / Task | 17.8s | 69.7s | 38.8s | 28.2s |

Key finding: **100% catch rate** on seeded flaws across all critic configs with **0% rubber-stamp rate**. Config D achieves this at lowest cost (2,852 tokens, 28.2s).

## 5. Architecture Diagram

```
Task Prompt
    │
    ▼
[ Planner ] ─────► Emits Plan (or Clarification Request)
    │
    ▼
[ Executor ] ────► Emits Code Patch + Internal Self-Reasoning
    │
    ▼
[ Context Assembler ] ──► STRIPS Executor Self-Reasoning & History
    │
    ▼
[ Critic ] ──────► Evaluates Raw Diff ONLY ──► Verdict (Approve / Revise)
    │
    ├── Approve ─────────────────────────► Approved Trajectory Record
    └── Revise & Round < 3 ──────────────► RevisionRequest ──► Re-prompt Executor
    └── Revise & Round >= 3 (Cap Hit) ───► EscalationResult (Human Review)
```
